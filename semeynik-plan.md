# Семейник — план приложения

Семейное приложение задумано с шестью разделами: Покупки, Бюджет, Планы, Фильмы, Рецепты, Вишлист. Первая версия (v1) включает только два раздела — **Покупки** и **Бюджет**. Планы, Фильмы, Рецепты и Вишлист полностью спроектированы ниже (модель данных и логика), но запланированы на следующие версии. Ниже — итоговая модель данных и логика по каждому разделу, плюс сквозные сущности.

*Версия 5 — в Бюджет добавлены кредиты и кредитные карты. Кредит объединён с подпиской в одну сущность «Регулярный платёж» с полем типа (похожая форма: фиксированная сумма, периодичность, дата, статус, напоминание). Кредитная карта — отдельная сущность (лимит и баланс долга зависят от трат по карте, а не фиксированы), в v1 реализована только как напоминание о платеже, без реального учёта баланса/лимита. Версия 4 — убран раздел «Дизайн-система» и все точечные визуальные/UI-детали по остальным разделам (цвета, анимации, названия UI-компонентов вроде чипсов/степперов/вкладок, раскладка экранов); план теперь описывает только данные, логику и функциональный состав экранов. Версия 3 — сужена область первой версии до Покупок и Бюджета; Планы, Фильмы, Рецепты и Вишлист вынесены в раздел "Следующие версии" — работа над ними не потеряна, просто не входит в v1. Версия 2 — по итогам ревью: единицы измерения в покупках, real-time синхронизация, передача владения семьёй, бюджетирование с лимитами и целями, доработана логика подписок/повторения планов/категоризации чеков/очереди фильмов, закрыты пробелы в вишлисте и авторизации, хранение файлов вынесено в отдельный сервис вне v1.*

## Область первой версии (v1)

**Входит в v1:** Покупки, Бюджет — вместе со сквозными сущностями (семья, пользователь, авторизация, синхронизация).

**Спроектировано, но не входит в v1:** Планы, Список фильмов, Список рецептов, Вишлист — см. раздел "Следующие версии" ниже.

Следствие сужения scope: интеграция "Добавить ингредиенты рецепта в покупки" в v1 не действует — раздела Рецепты ещё нет.

## Сквозные сущности

### Семья
- Название
- Дата создания

### Пользователь / Член семьи
- Имя, аватар (фото — вне v1, см. «Хранение файлов»), цвет, email/телефон, пароль (хэш)
- Цвет — свободный выбор пользователем, хранится в БД как строка "H S% L%" (например `"200 50% 60%"`, без обёртки `hsl()` — формат под CSS custom properties с поддержкой прозрачности); дубликаты цвета внутри одной семьи разрешены. При выборе приложение предупреждает, если цвет плохо читается (слишком светлый) или почти совпадает с акцентным цветом приложения, но не блокирует выбор
- Связь с семьёй — через связующую таблицу user↔family (даже если сейчас ограничение "одна семья на пользователя" держится на уровне логики приложения, а не структуры БД — чтобы не переделывать схему, если понадобится many-to-many)
- Роль внутри семьи (кроме технического "владелец") — отложено на будущее
- Управляемые детские профили без отдельного логина — отложено на будущее

### Авторизация
- Первый пользователь регистрируется → создаёт семью → становится владельцем
- Остальные присоединяются по инвайт-коду/ссылке с ограниченным сроком действия
- JWT (access + refresh токен)
- Восстановление пароля — код на email/телефон, стандартный сброс
- Смена email/телефона/пароля — в настройках профиля

### Владение и состав семьи
- Если владелец покидает семью или удаляет аккаунт — роль владельца автоматически переходит следующему участнику по дате присоединения
- Владелец может исключить участника из семьи

### Синхронизация
- Данные между устройствами членов семьи синхронизируются в реальном времени (WebSocket) — критично для сценариев вроде совместного похода в магазин по одному списку покупок
- Push-уведомления (FCM/APNs) — отдельный канал для случаев, когда приложение не открыто (напоминания по подпискам); WebSocket их не заменяет
- Операции над общими счётчиками (например, "куплено/нужно" в покупках) выполняются как атомарные инкременты/декременты на сервере, а не перезаписью абсолютного значения — иначе при одновременном редактировании несколькими участниками часть изменений потеряется
- Операции над эксклюзивными состояниями (например, бронь в вишлисте — актуально с выходом версии, где появится вишлист) выполняются как атомарная проверка-и-установка на сервере ("занять, только если сейчас свободно") — иначе возможно двойное срабатывание

### Хранение файлов
- Загрузка и хранение пользовательских файлов (аватарки, фото рецептов, сканы чеков) вынесены в отдельный сервис — в v1 его нет, поэтому в первой версии эти фичи полностью отсутствуют, а не работают на временном решении
- Постеры фильмов — не файл пользователя, а URL из внешнего API; не кешируются, к переносу в отдельный сервис отношения не имеют

## v1: Покупки

**Список покупок**: название, автор, статус (активен/завершён — переключается вручную), прогресс (N из M позиций закрыто).

**Позиция**: название, единица измерения (шт/кг/г/л/мл и т.п.), количество нужно, количество куплено (можно закрывать частично), позиция считается закрытой при куплено = нужно.

**Экран списков покупок**
- Поиск — по названию списка и по названию позиций внутри
- Списки группируются на активные и завершённые
- Сортировка: дата / автор / % завершённости

**Создание списка** — сразу открывается пустой список в режиме добавления позиций, без промежуточного экрана "введите название"; название по умолчанию, переименовывается позже.

**Экран одного списка**
- Заголовок показывает прогресс (N из M закрыто)
- Изменение количества купленного — по одному инкременту/декременту за раз; действие на "нужно" сразу закрывает позицию (куплено = нужно)
- Добавление позиции — с автодополнением по истории

## v1: Бюджет

**Транзакция**: сумма, дата, категория, тип (доход/расход), scope (личная/семейная), кто добавил, источник (вручную/скан чека), позиции чека (если скан).

**Регулярный платёж** (отдельный экран) — объединяет подписки и кредиты в одну сущность с полем типа: по форме это один и тот же периодический платёж с датой и статусом, разница только в смысле пары полей. Название, тип (подписка/кредит), сумма (для подписки — сумма списания за период; для кредита — сумма ежемесячного платежа), периодичность (месяц/год), дата следующего платежа, scope, статус (активен/завершён — для подписки «завершён» значит отменена, для кредита — погашен, в срок или досрочно), уведомление "за N дней до". Только для типа «кредит» (опционально, справочно, не участвует в расчётах v1): общая сумма кредита, дата окончания.

**Кредитная карта** (отдельный экран, отдельная сущность) — не объединена с регулярным платежом выше: там сумма фиксирована и известна заранее, а у карты сумма долга и доступный лимит зависят от того, сколько потратили по карте, — другая форма данных. В v1 это только напоминание о платеже, без реального учёта баланса/лимита по тратам: название/банк, сумма к оплате (вводится вручную, не рассчитывается), дата платежа, scope, статус (активна/закрыта), уведомление "за N дней до", кредитный лимит (опционально, справочно). Траты по карте — обычные транзакции бюджета, с картой напрямую не связаны.

**Разделение личный/семейный**
- Режимы "Мой" / "Семейный" переключаются явно, без объединённого вида
- Личные транзакции, регулярные платежи (подписки/кредиты) и кредитные карты полностью скрыты от других членов семьи (даже сумма)
- Scope выбирается в форме добавления транзакции и явно спрашивается после скана чека

**Сканер чеков** — реальный QR-код чека через стороннее API (уже есть готовая реализация).

**Автокатегоризация по чеку** — полностью офлайн, без внешних вызовов, один уровень (по продавцу):
1. Поиск продавца по ИНН в справочнике `merchant_category` — если найден, категория подставляется сразу
2. Если ИНН не найден — сопоставление названий позиций чека со словарём `keyword_category` (например "картошка" → Продукты), категория выбирается по наибольшему числу совпадений
3. Найденная по ключевым словам категория запоминается за этим ИНН — при следующем чеке от того же продавца сработает уже первый, более быстрый способ
4. Оба справочника (`merchant_category` и `keyword_category`) предзаполнены, но пользователь может дополнять своими категориями/ключевыми словами — они помечаются отдельно от системных, предзаполненных

Набор предзаполненных категорий и ключевых слов должен включать не только бытовые категории (продукты, коммуналка и т.д.), но и категории под строительный бизнес семьи (стройматериалы, инструменты) — раз чеки могут быть и по нему тоже.

**Категоризация — гибрид уровня транзакции и позиций.** У транзакции — одна основная категория (по продавцу/большинству совпадений, как описано выше) для ленты и агрегированной аналитики. Если чек был отсканирован и содержит разные позиции — в деталях транзакции доступна разбивка по позициям с их собственными категориями (например, чек из строительного магазина с "цементом" и "перчатками" — основная категория "Стройматериалы", но в деталях видно, что часть суммы — "Инструменты"), без влияния на агрегатную аналитику по основной категории.

**Логика подтверждения платежа** — общая для регулярных платежей (подписок и кредитов) и кредитных карт: в день платежа не создаётся транзакция автоматически; приходит уведомление с предложением подтвердить вручную. Если пользователь не отреагировал — через N дней приходит повторное уведомление, а платёж в интерфейсе помечается статусом "ожидает подтверждения" до тех пор, пока пользователь явно не подтвердит (создаётся транзакция на указанную сумму) или не отклонит.

**Бюджетирование (лимиты и цели)**
- Лимит по категории на месяц — задаётся вручную; на главном экране и на экране категории доступна информация "потрачено/лимит"
- Цели накопления/откладывания — отдельная сущность (название цели, целевая сумма, срок, текущий прогресс), пополняется вручную или привязкой части дохода

**Главный экран** (для текущего режима Мой/Семейный)
- Выбор отображаемого месяца
- Остаток за месяц (доход − расход)
- Сумма всех предстоящих платежей в месяц — регулярные платежи (подписки/кредиты) и кредитные карты вместе, с переходом на общий список (на уровне экрана — объединение двух сущностей, без общей таблицы в БД)
- Разбивка расходов по категориям
- Информация о бюджетных лимитах и целях накоплений на текущий месяц
- Список последних транзакций (в семейном режиме — с указанием, кто добавил)
- Действия: сканировать чек / добавить транзакцию вручную

## Следующие версии (спроектировано, не входит в v1)

### Планы

**План**: название, описание, дата, время начала-конца (или "весь день"), автор, scope (личный/семейный), правило повторения (нет/ежедневно/еженедельно с выбором дней недели/ежемесячно, опц. дата окончания), настройки уведомлений (тип: за период до / конкретное время-день; можно несколько).

**Видимость** — все члены семьи видят все планы, и личные, и семейные (в отличие от бюджета). Scope здесь влияет только на фильтрацию, а не на приватность.

**Редактирование** — план может редактировать только автор, независимо от scope.

**Повторение** — хранится как одна запись с правилом повторения, разворачивается "на лету" при отрисовке календаря; отдельные экземпляры не редактируются независимо (перенос одного дня — задел на будущее). Для еженедельного повторения можно выбрать конкретные дни недели (например, вт/чт), а не только "каждую неделю целиком".

**Экраны**
- Месяц: календарь с обозначением дней, где есть планы; переключение между месяцами; фильтр по членам семьи
- Неделя: обзор 7 дней с планами на выбранный день
- День: планы дня, упорядоченные по времени, с указанием длительности каждого

### Список фильмов

**Категория**: название (создаётся пользователем), автор. При удалении категории фильмы не удаляются и не блокируют удаление — переезжают в системную категорию "Без категории".

**Фильм**: название, постер/год/описание (подтягиваются через внешний API по названию), категория, кто добавил, статус (посмотрели/не посмотрели), приоритет (низкий/средний/высокий — тот же справочник, что и в вишлисте, для очереди "что посмотреть следующим"), оценки участников после просмотра.

Дата просмотра — не нужна.

**Экран**: фильмы группируются по категориям; отображается статус просмотра; непросмотренные сортируются по приоритету.

### Список рецептов

**Рецепт**: название, фото (вне v1, см. «Хранение файлов»), время приготовления, категория/кухня, кто добавил, ингредиенты (название/количество/единица), шаги приготовления (нумерованные, опц. таймер на шаг).

**Связка с Покупками** — действие "Добавить ингредиенты в покупки" на карточке рецепта; единица измерения и количество копируются в позицию покупок как есть, без конвертации и без пересчёта по порциям (порции не поддерживаются).

**Поиск** — по названию рецепта и по ингредиентам, аналогично поиску в покупках.

### Вишлист

**Позиция**: название, ссылка (опц.), цена (опц.), приоритет (низкий/средний/высокий), автор, статус брони (занято/свободно — видно только не-автору), кто забронировал (видно только другим, не автору).

Бронь можно снять — она возвращается в статус "свободно"; отменить бронь может тот, кто её поставил.

Добавление — только вручную (без автопарсинга по ссылке).

**Экран**: раздельный просмотр своего вишлиста и вишлистов других; в своём вишлисте бронь никак не видна (даже факт брони), в чужом — виден статус "занято" без указания кем.

## Открытые вопросы

- Что происходит с данными участника, который покидает семью или исключён из неё (его личные и семейные транзакции, позиции в списках, планы) — решение отложено, требует отдельного обсуждения. Актуально уже для v1 (Покупки, Бюджет).

## Отложено на будущее (сверх функциональности выше)

- Роли внутри семьи (взрослый/ребёнок с разными правами)
- Управляемые детские профили без логина
- User↔Family many-to-many на уровне БД (сейчас только в бизнес-логике)
- Редактирование отдельных экземпляров повторяющегося плана (исключения из правила)
- Автопарсинг позиции вишлиста по ссылке
- Дата просмотра фильма / история просмотров
- Порции в рецептах и пересчёт количества ингредиентов при переносе в покупки
- Полный RRULE-подобный конструктор повторения планов (произвольные интервалы, исключения)
- Полный справочник фасовок товаров для конвертации единиц измерения между рецептами и покупками
- Загрузка и хранение файлов (аватарки, фото рецептов, сканы чеков) — отдельный сервис, полностью вне v1
